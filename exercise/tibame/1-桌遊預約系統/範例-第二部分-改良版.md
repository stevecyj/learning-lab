# 桌遊預約系統（二）：用 SQLite 保存狀態的改良版

這份筆記講解 [ex-IMP-part2.ipynb](ex-IMP-part2.ipynb)，並接續[第一部分改良版](範例-第一部分-改良版.md)。

第一部分把預約狀態放在字典裡；程式一結束，資料就消失。第二部分保留原本的對話規則，但把狀態移進 SQLite 資料庫，並補上可重複初始化、交易回復、連線關閉，以及多人同時預約時不互相覆寫的處理。

## 這一部分要練會什麼

- 把 Python 字典的資料模型改成 SQLite 資料表。
- 分清楚 Python 的 `None` 與 SQL 的 `NULL`。
- 用 `?` 傳入 SQL 參數，不把使用者資料拼進 SQL 字串。
- 用 `commit()` 確認變更，用 `rollback()` 撤銷失敗的交易。
- 用條件式 `UPDATE` 完成「只有尚未預約時才能預約」。
- 用 `rowcount` 判斷這次更新是否真的成功。
- 不論程式如何離開主迴圈，都用 `finally` 關閉連線。

## 從第一部分到第二部分

| 第一部分：記憶體字典 | 第二部分：SQLite |
| --- | --- |
| `games[game_name]` | 資料表中的一列 |
| 字典 key | `game_name` 欄位 |
| 字典 value | `reserved_by_user_id` 欄位 |
| `None` | SQL `NULL` |
| `games[game_name] = user_id` | `UPDATE ... SET reserved_by_user_id = ?` |
| 關閉程式後資料消失 | 關閉程式後資料仍留在 `.db` 檔案 |

資料存放位置改了，但預約狀態仍只有兩種：

```text
可預約：reserved_by_user_id 是 NULL
    │ 預約
    ▼
已預約：reserved_by_user_id 是某位使用者的 ID
    │ 取消
    └──────────────────────────────► 回到 NULL
```

## 完整程式

```python
import sqlite3
from pathlib import Path

DEFAULT_GAMES = ("卡卡頌", "花磚物語", "璀璨寶石")
current_user_id = "123abc"

# 這段程式預期你從以下其中一個位置啟動 Jupyter：
# 1. repo 根目錄（整個專案最外層）：使用下方指定的題目資料夾。
# 2. 這份 .ipynb 所在的題目資料夾：直接使用 Jupyter 的目前目錄。
# 因此，game_reservations.db 都會和這份 .ipynb 放在同一個資料夾。
exercise_directory = Path("exercise/tibame/1-桌遊預約系統")
database_directory = exercise_directory if exercise_directory.is_dir() else Path.cwd()
DB_PATH = database_directory / "game_reservations.db"


def initialize_database(connection):
    """建立資料表，並只補上尚未存在的預設遊戲。"""
    # 字典初始化改為可重複執行的建表與 seed；不會清空既有預約。
    connection.execute(
        """
        CREATE TABLE IF NOT EXISTS game_reservation_states (
            id INTEGER PRIMARY KEY,
            game_name TEXT NOT NULL UNIQUE,
            reserved_by_user_id TEXT
        )
        """
    )
    connection.executemany(
        """
        INSERT INTO game_reservation_states (game_name)
        VALUES (?)
        ON CONFLICT(game_name) DO NOTHING
        """,
        ((game_name,) for game_name in DEFAULT_GAMES),
    )
    connection.commit()


def find_game_names(connection, message):
    """找出出現在使用者訊息中的遊戲名稱。"""
    rows = connection.execute(
        """
        SELECT game_name
        FROM game_reservation_states
        ORDER BY id
        """
    ).fetchall()
    matched_games = [
        row["game_name"]
        for row in rows
        if row["game_name"] in message
    ]  # fmt: skip
    return matched_games


def end_service():
    """服務結束"""
    print("服務結束")


def show_database_error(connection, error):
    """回復失敗的資料庫操作並顯示錯誤。"""
    connection.rollback()
    print(f"資料庫操作失敗：{error}")


def cancel_reservations(connection):
    """取消目前使用者的所有預約。"""
    try:
        rows = connection.execute(
            """
            SELECT game_name
            FROM game_reservation_states
            WHERE reserved_by_user_id = ?
            ORDER BY id
            """,
            (current_user_id,),
        ).fetchall()
        canceled_games = [row["game_name"] for row in rows]

        if len(canceled_games) == 0:
            print("你目前沒有預約。")
            return

        # 字典逐項設為 None，改成一次 UPDATE 並以一次 commit 完成。
        connection.execute(
            """
            UPDATE game_reservation_states
            SET reserved_by_user_id = NULL
            WHERE reserved_by_user_id = ?
            """,
            (current_user_id,),
        )
        connection.commit()

        game_text = "、".join(canceled_games)
        print(f"已取消預約：{game_text}")
    except sqlite3.Error as error:
        show_database_error(connection, error)


def show_available_games(connection):
    """顯示所有尚未被預約的遊戲。"""
    try:
        # 字典篩選 None，改成使用 WHERE ... IS NULL 查詢。
        rows = connection.execute(
            """
            SELECT game_name
            FROM game_reservation_states
            WHERE reserved_by_user_id IS NULL
            ORDER BY id
            """
        ).fetchall()
        available_games = [row["game_name"] for row in rows]

        if len(available_games) == 0:
            print("目前沒有可預約的遊戲。")
        else:
            game_text = "\n".join(available_games)
            print(f"目前可預約的遊戲：\n{game_text}")
    except sqlite3.Error as error:
        show_database_error(connection, error)


def show_unknown_command():
    """無法理解指令"""
    print("我不明白這個指令。")
    print("你可以查看遊戲、預約遊戲、取消預約，或輸入「結束」。")


def reserve_game(connection, message):
    """從訊息中找出遊戲，然後為目前使用者預約。"""
    try:
        matched_games = find_game_names(connection, message)

        if len(matched_games) == 0:
            print("找不到遊戲名稱，請說明想預約哪一款遊戲。")
            return

        if len(matched_games) > 1:
            game_text = "、".join(matched_games)
            print(f"你提到了多款遊戲：{game_text}，請一次指定一款。")
            return

        game_name = matched_games[0]

        # 字典指定使用者，改成只在尚未預約時才成功的原子 UPDATE。
        cursor = connection.execute(
            """
            UPDATE game_reservation_states
            SET reserved_by_user_id = ?
            WHERE game_name = ?
              AND reserved_by_user_id IS NULL
            """,
            (current_user_id, game_name),
        )

        if cursor.rowcount == 1:
            connection.commit()
            print(f"已為你預約：{game_name}")
            return

        row = connection.execute(
            """
            SELECT reserved_by_user_id
            FROM game_reservation_states
            WHERE game_name = ?
            """,
            (game_name,),
        ).fetchone()
        connection.commit()

        if row is None:
            print("找不到遊戲名稱，請說明想預約哪一款遊戲。")
        elif row["reserved_by_user_id"] == current_user_id:
            print(f"你已經預約過：{game_name}")
        else:
            print(f"{game_name} 已被其他使用者預約。")
    except sqlite3.Error as error:
        show_database_error(connection, error)


def main():
    connection = None

    try:
        connection = sqlite3.connect(DB_PATH)
        connection.row_factory = sqlite3.Row
        initialize_database(connection)
    except sqlite3.Error as error:
        if connection is not None:
            connection.close()
        print(f"資料庫初始化失敗：{error}")
        return

    try:
        while True:
            msg = input("輸入訊息: ").strip()

            if msg == "結束":
                end_service()
                break
            elif "取消" in msg:
                cancel_reservations(connection)
            elif "預約" in msg or "訂" in msg:
                reserve_game(connection, msg)
            elif "遊戲" in msg or "有哪些" in msg:
                show_available_games(connection)
            else:
                show_unknown_command()
    finally:
        # 交易在各操作完成時 commit；服務結束時關閉長連線。
        connection.close()


main()
```

## 資料表就是新的狀態容器

第一部分用這個字典表示狀態：

```python
games = {
    "卡卡頌": None,
    "花磚物語": None,
    "璀璨寶石": None,
}
```

第二部分改成 `game_reservation_states` 資料表。初始化後，它的內容可想成：

| id | game_name | reserved_by_user_id |
| ---: | --- | --- |
| 1 | 卡卡頌 | `NULL` |
| 2 | 花磚物語 | `NULL` |
| 3 | 璀璨寶石 | `NULL` |

建表語法同時寫下資料必須遵守的規則：

```sql
CREATE TABLE IF NOT EXISTS game_reservation_states (
    id INTEGER PRIMARY KEY,
    game_name TEXT NOT NULL UNIQUE,
    reserved_by_user_id TEXT
)
```

- `id INTEGER PRIMARY KEY`：每列有不重複的整數識別碼；新增資料時可由 SQLite 產生。
- `game_name TEXT NOT NULL UNIQUE`：名稱必須存在，而且同名遊戲不能重複。
- `reserved_by_user_id TEXT`：沒有寫 `NOT NULL`，所以可存 `NULL`，表示尚未預約。
- `IF NOT EXISTS`：資料表已存在時不再建立，因此重新執行 Notebook 不會立刻出現「table already exists」。

`PRIMARY KEY`、`NOT NULL` 和 `UNIQUE` 都是資料庫約束。它們不是給人看的註解，而是 SQLite 會實際執行的防線。正式語意可查 [SQLite CREATE TABLE](https://www.sqlite.org/lang_createtable.html)。

## 資料庫檔案會放在哪裡

```python
exercise_directory = Path("exercise/tibame/1-桌遊預約系統")
database_directory = exercise_directory if exercise_directory.is_dir() else Path.cwd()
DB_PATH = database_directory / "game_reservations.db"
```

`Path` 用物件表示檔案路徑。`/` 在這裡不是除法，而是把目錄和檔名接起來：

```python
Path("exercise") / "game_reservations.db"
```

這段程式支援課程中最常見的兩種啟動位置：

| 啟動 Jupyter 時的工作目錄 | `DB_PATH` 的結果 |
| --- | --- |
| repo 根目錄 | `exercise/tibame/1-桌遊預約系統/game_reservations.db` |
| 題目目錄 | 目前目錄下的 `game_reservations.db` |

相對路徑是從「目前工作目錄」解讀，不是自動從 notebook 檔案所在位置解讀。若從其他任意目錄啟動，這個 fallback 會把資料庫放到那個目錄。遇到「資料怎麼不見了」時，先執行：

```python
print(Path.cwd())
print(DB_PATH.resolve())
```

這通常能找出是不是開到了另一個 `.db` 檔案。`Path.cwd()`、`is_dir()` 與路徑組合可查 [Python `pathlib` 文件](https://docs.python.org/3.11/library/pathlib.html)。

## 開啟連線，讓查詢結果可以用欄位名稱讀取

```python
connection = sqlite3.connect(DB_PATH)
connection.row_factory = sqlite3.Row
```

`sqlite3.connect()` 會開啟資料庫連線；檔案不存在時會建立它。`DB_PATH` 是 `Path` 物件，`sqlite3.connect()` 可以直接接受 path-like object。

預設查詢結果是 tuple：

```python
row[0]
```

設定 `sqlite3.Row` 後，同一欄可以用名稱讀取：

```python
row["game_name"]
```

欄位名稱比數字索引更能表達意思，也不容易在調整 `SELECT` 欄位順序後讀錯。官方文件也建議在 connection 上設定 `row_factory`，讓之後建立的 cursor 採用同一規則；參考 [Python `sqlite3` 的 row factory 說明](https://docs.python.org/3.11/library/sqlite3.html#how-to-create-and-use-row-factories)。

這份程式沒有先寫：

```python
cursor = connection.cursor()
```

而是直接使用：

```python
connection.execute(...)
```

這是 connection 的快捷方法。它仍會建立並回傳 cursor，所以後面才能讀取 `cursor.rowcount`。兩種寫法都有效；這份小程式用快捷方法可以少管理一個長期存在的 cursor。

## 初始化必須能安全重跑

Notebook 很常重複執行同一格。如果初始化每跑一次就插入三款遊戲，資料會不斷重複；如果每次先清空資料，又會讓既有預約消失。

這個版本選擇「只補缺少的遊戲」：

```python
connection.executemany(
    """
    INSERT INTO game_reservation_states (game_name)
    VALUES (?)
    ON CONFLICT(game_name) DO NOTHING
    """,
    ((game_name,) for game_name in DEFAULT_GAMES),
)
```

`executemany()` 會替 `DEFAULT_GAMES` 中的每款遊戲執行一次 `INSERT`。每次需要一組參數，所以資料長這樣：

```python
("卡卡頌",)
("花磚物語",)
("璀璨寶石",)
```

單一元素 tuple 的逗號不能省略；`("花磚物語")` 仍只是字串，`("花磚物語",)` 才是 tuple。

`game_name` 有 `UNIQUE` 約束。若名稱已存在，`ON CONFLICT(game_name) DO NOTHING` 會略過那次新增，不改動原本那列。因此：

- 第一次執行：建立三款遊戲。
- 第二次執行：三款都已存在，全部略過。
- 之後把一款新遊戲加入 `DEFAULT_GAMES`：只補上新遊戲。
- 原本已有預約：保留原本的 `reserved_by_user_id`。

同一個初始化動作執行多次仍得到相同結果，稱為「可重複執行」或 idempotent。`ON CONFLICT ... DO NOTHING` 的規則可查 [SQLite UPSERT](https://www.sqlite.org/lang_upsert.html)。

最後的：

```python
connection.commit()
```

會提交 seed 所造成的新增，讓其他連線與下次啟動都能看到它們。

## 查詢時只取真正需要的欄位

```python
rows = connection.execute(
    """
    SELECT game_name
    FROM game_reservation_states
    ORDER BY id
    """
).fetchall()
```

這裡沒有使用 `SELECT *`，因為尋找名稱只需要 `game_name`。`fetchall()` 把所有查詢結果取回成一個 list；每個元素因為 `row_factory` 的設定而是 `sqlite3.Row`。

`ORDER BY id` 讓顯示與匹配順序固定。如果沒有 `ORDER BY`，不要依賴資料庫碰巧回傳的列順序。

接著仍沿用第一部分的子字串搜尋：

```python
matched_games = [
    row["game_name"]
    for row in rows
    if row["game_name"] in message
]
```

SQLite 負責保存與取出遊戲清單，Python 負責判斷遊戲名稱是否出現在訊息裡。這種分工在目前只有三款遊戲時很清楚。第一部分筆記已討論清單很大時的搜尋成本，這裡不重複展開。

## `None` 與 `NULL` 是兩個世界的空值

| 使用位置 | 空值寫法 |
| --- | --- |
| Python 程式 | `None` |
| SQL 指令 | `NULL` |
| SQL 判斷空值 | `IS NULL` |

查詢可預約遊戲時寫：

```sql
SELECT game_name
FROM game_reservation_states
WHERE reserved_by_user_id IS NULL
```

不能改成：

```sql
WHERE reserved_by_user_id = NULL
```

`NULL` 表示缺少或未知的值，不能用一般等號判斷；SQL 要用 `IS NULL` 或 `IS NOT NULL`。

取消預約時，程式直接在 SQL 裡寫 `NULL`：

```sql
UPDATE game_reservation_states
SET reserved_by_user_id = NULL
WHERE reserved_by_user_id = ?
```

也可以透過參數傳入 Python 的 `None`，`sqlite3` 會把它綁定成 SQL `NULL`：

```python
connection.execute(
    "UPDATE game_reservation_states SET reserved_by_user_id = ? WHERE game_name = ?",
    (None, game_name),
)
```

## SQL 參數要和 SQL 字串分開

```python
connection.execute(
    """
    SELECT game_name
    FROM game_reservation_states
    WHERE reserved_by_user_id = ?
    """,
    (current_user_id,),
)
```

`?` 是值的位置，`(current_user_id,)` 是另外交給資料庫驅動程式的參數。不要這樣拼字串：

```python
# 不要這樣做
sql = f"SELECT game_name FROM game_reservation_states WHERE reserved_by_user_id = '{current_user_id}'"
```

參數綁定有兩個好處：

1. 驅動程式會正確處理引號與特殊字元。
2. 使用者資料不會被當成 SQL 語法執行，可避免 SQL injection。

參數數量必須和 `?` 數量相同：

```python
(current_user_id, game_name)  # 對應兩個 ?
(current_user_id,)            # 對應一個 ?
```

這是 Python 官方文件明確建議的用法；參考 [`sqlite3` placeholders](https://docs.python.org/3.11/library/sqlite3.html#how-to-use-placeholders-to-bind-values-in-sql-queries)。

## 取消預約：先記住名稱，再一次更新

取消流程先查出目前使用者預約的遊戲：

```python
rows = connection.execute(
    """
    SELECT game_name
    FROM game_reservation_states
    WHERE reserved_by_user_id = ?
    ORDER BY id
    """,
    (current_user_id,),
).fetchall()
canceled_games = [row["game_name"] for row in rows]
```

如果沒有資料，立即回應並結束函式：

```python
if len(canceled_games) == 0:
    print("你目前沒有預約。")
    return
```

有資料時，用一個 `UPDATE` 取消這位使用者的全部預約：

```sql
UPDATE game_reservation_states
SET reserved_by_user_id = NULL
WHERE reserved_by_user_id = ?
```

第一部分需要走訪字典，逐項指定 `None`；資料庫可以直接更新所有符合 `WHERE` 的列。程式先保存 `canceled_games`，是因為更新後那些列已不再帶有這位使用者的 ID，仍需要原本的名稱才能顯示「已取消預約：……」。

## 預約的關鍵：把檢查與修改放進同一個 `UPDATE`

直覺寫法通常是先查詢，再更新：

```python
# 概念示意：有多人同時操作時不夠穩妥
row = connection.execute(
    "SELECT reserved_by_user_id FROM game_reservation_states WHERE game_name = ?",
    (game_name,),
).fetchone()

if row["reserved_by_user_id"] is None:
    connection.execute(
        "UPDATE game_reservation_states SET reserved_by_user_id = ? WHERE game_name = ?",
        (current_user_id, game_name),
    )
```

如果使用者 A 和 B 幾乎同時操作，可能發生：

| 時間 | 使用者 A | 使用者 B |
| ---: | --- | --- |
| 1 | 查到尚未預約 |  |
| 2 |  | 也查到尚未預約 |
| 3 | 寫入 A |  |
| 4 |  | 寫入 B，蓋掉 A |

問題出在「檢查」和「修改」是兩個分開的 SQL statement，中間留有其他操作插入的空窗。

改良版把條件直接寫進 `UPDATE`：

```python
cursor = connection.execute(
    """
    UPDATE game_reservation_states
    SET reserved_by_user_id = ?
    WHERE game_name = ?
      AND reserved_by_user_id IS NULL
    """,
    (current_user_id, game_name),
)
```

這句話的意思是：

> 把指定遊戲的預約者設為目前使用者，但只有該遊戲現在仍是 `NULL` 時才修改。

SQLite 會把一個 `UPDATE` statement 當成不可拆開的操作。SQLite 同一時間只允許一個寫入交易；其他寫入者會等待，或在等候逾時時收到鎖定錯誤。條件放進同一個 `UPDATE`，可避免後來的寫入者使用舊查詢結果覆蓋先成功的人。可搭配閱讀 [SQLite UPDATE](https://www.sqlite.org/lang_update.html) 與 [Transactions](https://www.sqlite.org/lang_transaction.html)。

這裡的「原子」不是指永遠不會遇到鎖定錯誤，而是指這次判斷與修改不會被拆成兩段。程式已用 `except sqlite3.Error` 接住資料庫錯誤，但尚未加入忙碌時的重試策略。

## `rowcount` 把資料庫結果帶回程式流程

條件式更新有兩種結果：

```python
if cursor.rowcount == 1:
    connection.commit()
    print(f"已為你預約：{game_name}")
    return
```

| `cursor.rowcount` | 意思 |
| ---: | --- |
| `1` | 找到指定遊戲，而且原本是 `NULL`；預約成功 |
| `0` | 沒有任何列同時符合遊戲名稱與 `IS NULL` |

Python 官方文件把 `rowcount` 定義為 `INSERT`、`UPDATE`、`DELETE`、`REPLACE` 修改的列數；參考 [`Cursor.rowcount`](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.Cursor.rowcount)。

`rowcount == 0` 只知道「沒有更新」，還不知道原因，所以程式再查一次：

```python
row = connection.execute(
    """
    SELECT reserved_by_user_id
    FROM game_reservation_states
    WHERE game_name = ?
    """,
    (game_name,),
).fetchone()
```

接著把資料狀態翻成使用者看得懂的訊息：

```python
if row is None:
    print("找不到遊戲名稱，請說明想預約哪一款遊戲。")
elif row["reserved_by_user_id"] == current_user_id:
    print(f"你已經預約過：{game_name}")
else:
    print(f"{game_name} 已被其他使用者預約。")
```

`row is None` 在正常流程中很少發生，因為遊戲名稱剛剛才從同一張表讀出來；它仍是一個合理的防守分支，可處理資料在兩次 statement 之間被其他工具刪除的情況。

## `commit()` 與 `rollback()` 決定一批變更的命運

資料庫異動不是執行完 `UPDATE` 就可以不管。這份程式明確採用：

```text
操作成功 ──► commit()   ──► 確認保留交易中的變更
操作失敗 ──► rollback() ──► 撤銷尚未提交的變更
```

成功路徑會提交：

```python
connection.commit()
```

錯誤路徑集中處理：

```python
def show_database_error(connection, error):
    connection.rollback()
    print(f"資料庫操作失敗：{error}")
```

若一個操作中途失敗，只印錯誤卻不 `rollback()`，連線可能仍停在失敗或未完成的交易中，影響後面的操作。`rollback()` 在沒有待處理交易時不會造成額外變更，所以讀取函式共用這個錯誤處理也可以。

Python 3.11 的 `sqlite3` 在預設交易模式下，執行 `INSERT`、`UPDATE`、`DELETE` 或 `REPLACE` 時會視需要隱含開啟交易；`commit()` 和 `rollback()` 分別提交及回復待處理交易。詳見 [Python `sqlite3` transaction control](https://docs.python.org/3.11/library/sqlite3.html#transaction-control)。

## 為什麼每個資料庫函式都有 `connection` 參數

第一部分的函式直接讀寫全域字典：

```python
def show_available_games():
    ...
```

第二部分明確收到連線：

```python
def show_available_games(connection):
    ...
```

這能讓函式知道自己要操作哪個資料庫，也方便測試時傳入 `sqlite3.connect(":memory:")`。它比在每個函式內重新開啟連線更容易維持同一個操作期間的交易狀態。

`current_user_id` 目前仍是全域變數，因為這一版延續第一部分的單一使用者情境。若下一步要支援登入使用者，較好的介面會是：

```python
def reserve_game(connection, user_id, message):
    ...
```

這樣函式不會暗中依賴固定的 `"123abc"`。

## `main()` 管理連線的一生

```python
def main():
    connection = None
```

先設成 `None`，是因為連線建立本身也可能失敗。錯誤處理時可以安全判斷是否真的有連線可關：

```python
except sqlite3.Error as error:
    if connection is not None:
        connection.close()
    print(f"資料庫初始化失敗：{error}")
    return
```

初始化成功後才進入對話迴圈。迴圈放在 `try` 裡，關閉連線放在 `finally`：

```python
try:
    while True:
        ...
finally:
    connection.close()
```

因此不只輸入「結束」會關閉連線；即使 `input()` 收到中斷，或迴圈內發生未預期的非 SQLite 例外，`finally` 仍會執行。`close()` 不等於 `commit()`，所以資料異動已在各操作成功時先提交。

Notebook 最後直接呼叫：

```python
main()
```

這適合互動練習。日後移到 `.py` 模組並可能被其他檔案匯入時，可改成：

```python
if __name__ == "__main__":
    main()
```

如此匯入函式時不會立刻進入 `input()` 迴圈。

## 領域專家會再檢查的邊界

這個版本已比單純的教學範例穩健，但還不是完整的多人預約服務。

### 資料庫目前只保證遊戲名稱不重複

`UNIQUE(game_name)` 防止同一款遊戲出現兩列，但沒有禁止同一位使用者預約多款遊戲。這正好符合目前「取消該使用者全部預約」的規則。若產品規則改成「一人只能預約一款」，必須新增相應約束或交易邏輯，不能只改提示文字。

### 可重複 seed 不等於完整 migration

把新名稱加入 `DEFAULT_GAMES` 可以補資料，但從 tuple 刪除名稱不會刪除資料庫中的舊遊戲；改名也會被視為新增另一款。正式系統需要明確的 schema 與資料 migration。

另外，`CREATE TABLE IF NOT EXISTS` 只檢查同名資料表是否存在，不會自動把舊表改成最新欄位。未來 schema 改變時仍要處理版本升級。

### 原子更新保護資料，但不等於完整並行策略

條件式 `UPDATE` 可避免覆寫已成功的預約。不過多個程序同時寫 SQLite 時仍可能遇到 `database is locked`；目前只回報錯誤，沒有設定重試、退避或忙碌逾時策略。

而且失敗後為了解釋原因所做的 `SELECT`，只代表那一刻看到的狀態。若有大量並行操作，資料正確性仍受保護，但提示文字可能很快過時。

### 後端服務不應任意共享同一條連線

目前是一個 CLI 迴圈持有一條連線，結構合理。日後接上多執行緒後端時，不應直接把這條 connection 當成所有請求共用的全域物件；Python `sqlite3.connect()` 預設會檢查 connection 是否在建立它的同一執行緒使用。屆時要依框架生命週期建立每個請求或工作單位的連線。

### 顯示原始資料庫錯誤只適合練習環境

```python
print(f"資料庫操作失敗：{error}")
```

CLI 練習時能快速取得回饋。正式服務通常會把詳細錯誤寫入內部 log，對使用者只回傳不洩漏路徑、schema 或內部狀態的訊息。

## 動手驗證：先猜，再執行

下面的短程式使用記憶體資料庫，不會建立檔案。先猜三個 `print()` 的結果，再執行核對：

```python
import sqlite3

connection = sqlite3.connect(":memory:")
connection.execute(
    """
    CREATE TABLE reservations (
        game_name TEXT PRIMARY KEY,
        reserved_by_user_id TEXT
    )
    """
)
connection.execute(
    "INSERT INTO reservations (game_name) VALUES (?)",
    ("花磚物語",),
)

first = connection.execute(
    """
    UPDATE reservations
    SET reserved_by_user_id = ?
    WHERE game_name = ? AND reserved_by_user_id IS NULL
    """,
    ("user-a", "花磚物語"),
)
second = connection.execute(
    """
    UPDATE reservations
    SET reserved_by_user_id = ?
    WHERE game_name = ? AND reserved_by_user_id IS NULL
    """,
    ("user-b", "花磚物語"),
)
row = connection.execute(
    "SELECT reserved_by_user_id FROM reservations WHERE game_name = ?",
    ("花磚物語",),
).fetchone()

print(first.rowcount)
print(second.rowcount)
print(row[0])

connection.close()
```

# 8-4 認識外來鍵 (Foreign Key)

來源：`8-4-認識外來鍵.vtt`

這堂課沒有教 SQL 寫法。外來鍵為什麼存在、它約束什麼、沒有約束時資料會怎樣，才是重點。細節設定老師說之後才會講，這裡不補。

---

## 1. 這堂課真正要解決的問題

兩張表要對得上號，對到的那一端還必須真的存在。

書表需要出版社編號，因為書店之後要再訂同一本書時，必須知道該找哪一家出版社、打給誰。出版社編號不是書自己的屬性。沒有這個編號，兩張表就是兩堆互不相干的列。

只把編號抄過去還不夠。若書表可以填一個出版社表裡不存在的編號，或出版社列還被書引用卻被刪掉，之後再訂購會對到空的。老師把這種狀況叫**斷頭資料**：有參照、沒有頭、接不到聯絡資訊。

外來鍵（foreign key，簡稱 FK）就是資料庫用來擋住這兩種斷頭的約束。

---

## 2. 核心概念

### 概念 1：外來鍵是為了關聯而放進來的欄位

外來鍵是出現在「不該屬於這張表」上的識別欄。書表本來該有書編號、書名、定價、作者；出版社編號是出版社表的資料，卻被放到書表，所以叫「外來」。

兩張表要互相參照時才需要它：書要能指向某一家出版社。沒有這個欄位，書賣完要再訂時，不知道該找哪一家、打給哪個聯絡人。課堂只處理需要關聯的情況；何時不該用，逐字稿沒講。

### 概念 2：FK 是 constraint

FK 跟主鍵（PK）一樣，是限制／約束。設了之後，資料庫管理系統會要求你指定：這個欄位參照哪一張表的哪一個欄位。

光有同名欄位，系統不會檢查對不對得上。約束把「必須對得上」寫進資料庫，避免應用程式或人工輸入寫出對不到的編號。兩張表的關係必須一直成立時才設；不能靠「記得對一下」。老師只說詳細設定之後再講，沒有討論何時不建 FK。

### 概念 3：被參照的欄位必須具有唯一性

FK 指向的那一端，必須能唯一找出一筆。課堂給了兩種：主鍵（PK），以及不是 PK 但仍唯一的唯一鍵（unique key）。

參照的目的是對到那一筆。若被參照欄可以重複，同一個編號可能對到兩家出版社，關聯就沒有單一答案。課堂的順序是：出版社的出版社 id 先成為 PK（或至少有唯一性），書表的出版社 id 才能被設成 FK。沒有 PK、也沒有其他唯一性限制的欄位，就不能被參照。系統會拒絕。

### 概念 4：新增時，FK 的值必須在被參照表裡已經存在

新增一本書時，填進去的出版社 id 必須是出版社表裡已經有的值。課堂例子：出版社沒有 `p003`，書卻填 `p003`，新增失敗。書不能屬於一家不存在的出版社。

FK 設好之後，每次對子表（書）做新增都會走這條檢查。欄位可否為空、之後才補出版社，課堂沒講。

### 概念 5：被參照的那一筆不能刪

出版社 `p001` 已被第一本書（課堂例子是 *Head First Java*）參照，這筆出版社就不能刪。頭被砍掉，身體上的編號還在，一樣是斷頭。書賣完要再訂時，找不到該打給誰。

FK 設好之後，刪被參照表（出版社）的列時會走這條檢查。老師明確說詳細設定之後才講，所以「刪出版社時要不要連帶刪書、改成空值」不在本堂範圍。本堂只教到：有被參照就不准刪。

### 概念 6：斷頭資料

斷頭資料是本堂用來稱呼這種狀態的詞，不是 MySQL 關鍵字：參照欄有值，被參照的那一端卻沒有對應列。沒有頭、接不到頭，也就不知道頭上的名稱、電話、地址。

它是 FK 要預防的結果。課堂講了兩種來源：新增時填不存在的編號；刪除時把已被參照的列刪掉。檢查資料模型或除錯時，用它判斷這筆關聯還能不能走到完整資訊。沒有 FK、兩張表本來就無關聯，只是兩張獨立表，不要叫斷頭。

## 3. Mental Model

把出版社那一筆想成「頭」，書上的出版社編號想成「指向頭的手指」。FK 只保證手指指得到一顆真實存在、而且唯一的頭。它不會把兩張表的內容合併顯示。

```text
出版社表（被參照／頭）
  p001  ──唯一──►  這一筆的名稱、電話、地址
  p002  ──唯一──►  另一筆

書表（參照端／身體）
  書A.publisher_id = p001  ──FK──►  只能指向上面那顆頭
  書B.publisher_id = p002
```

新增一本書時，系統會先問出版社表：這個值在不在、能不能唯一對到一筆。

```text
要新增書（publisher_id = X）
        │
        ▼
出版社表裡有唯一的 X？
   ├─ 有 → 寫入書表
   └─ 沒有 → 新增失敗（預防斷頭）
```

刪一筆出版社時，方向相反：先問書表有沒有人還指著它。

```text
要刪出版社（publisher_id = X）
        │
        ▼
有沒有書的 FK 仍等於 X？
   ├─ 有 → 刪除失敗（預防斷頭）
   └─ 沒有 → 可以刪
```

這兩張流程圖依賴課堂假設：出版社 id 已經是 PK（因此唯一），書的出版社 id 已經設成 FK，ON DELETE 之類的詳細設定先不談。

## 4. 專家視角

### 初學者需要知道，但資深工程師通常不會特別思考的內容

- 「外來」指的是欄位的歸屬，不是資料從別的資料庫匯入。出版社編號對書來說是外來的，因為它的定義在出版社表。
- 兩張表有同名欄位，人看起來像有關係；constraint 才會讓系統拒絕壞資料。
- 建 FK 的前置條件是被參照端先有唯一性。先建書表的 FK、出版社 id 卻還只是普通欄位，課堂的規則下做不到。
- 斷頭的後果是要訂購時沒有可聯絡的對象。

### 即使是資深工程師仍然會注意的內容

- 關聯方向：子表存父表的識別值（書存出版社 id）。父表去存子表的識別值，約束會擋錯邊。
- 唯一性是參照能成立的前提。PK 是最直接的做法；unique key 也可以。被參照端若允許重複，關聯沒有單一目標。
- 約束會同時限制「寫入子表」和「刪除父表」。刪父資料會變成顯式失敗，而不是默默留下無效編號。
- 本堂的刪除行為是「被參照就不准刪」。專案裡還常要決定：拒絕刪、連帶刪、還是把子表欄位清空。老師把這塊標成之後才說。現在若當成「FK 只有這一種刪除行為」，範圍會超出課堂。

## 5. 語法 vs 通用知識

### 語言特有知識

名稱：foreign key / FK、constraint、primary key / PK、unique key。

MySQL（以及這門課用的資料庫管理系統）在建立 FK 時會要求你指出參照哪一張表的哪一個欄位，且該欄必須有唯一性。設成 FK 之後，新增子列、刪除父列會被系統擋下。具體 SQL 語法、錯誤訊息、以及 ON DELETE / ON UPDATE 等選項，逐字稿未涵蓋。

### 通用程式設計知識

書只存出版社編號；名稱、電話、地址留在出版社表。物件裡對應的做法是存 id 或參考，不要複製整份物件；API 裡則是訂單只帶 `customer_id`。

參照完整性：指向必須指向還存在、且可唯一定位的目標。沒有這層保證，就會出現課堂說的斷頭資料。JavaScript 裡對應直覺是：變數還拿著一個 id，但對應的物件已經從 Map 裡刪掉。

老師強調這是 DBMS 的限制。換 Python、Java 或前端表單，若只有程式自己檢查，繞過程式直接改資料仍可能寫出斷頭；FK 是資料庫自己擋。

## 6. Trade-off

課堂幾乎沒有把兩種都合理的設計並列比較。有講到的分叉只有下面兩個。

### A. 被參照端用 PK vs 用 unique key

| | PK | unique key |
| --- | --- | --- |
| 差異 | 主鍵，最直接的唯一性 | 不是 PK，但仍唯一 |
| 好處 | 課堂說「最直接就是 PK」；出版社 id 當 PK 後一定唯一，FK 可以建 | 某個不是主鍵的欄位若業務上仍唯一，也能當被參照端 |
| 成本 | 一張表通常只有一個 PK，要把「被別人參照的那個識別」放進主鍵設計裡 | 要另外設唯一限制；課堂沒講它和 PK 在關聯上還有什麼行為差別 |
| 適合 | 出版社 id 本來就是這張表的識別 | 識別不是主鍵、但你仍要別人來參照這個唯一欄 |
| 選錯的後果 | 沒有任何唯一性 → 不能被參照，FK 建不起來 | 誤以為「不是 PK 就不能當 FK 目標」→ 選項變窄；或誤以為普通欄位也行 → 建不起來 |

### B. 書表放出版社編號（才能關聯）vs 覺得它不該屬於書

老師自己也說這個欄位「怪怪的」，但它必須建立，否則兩張表沒有關聯、無法訂購。代價是書表出現一個概念上屬於別張表的欄。不放就無法訂購。

課堂裡不建 FK 約束就會變成斷頭資料。沒有討論效能、分散式、或「先不建 FK」的合法情境。

## 7. 常見誤解

1. **有同名欄位就等於有外來鍵。** 書表可以有一個叫出版社編號的欄，但沒設 FK 約束時，系統不會擋 `p003` 這種不存在的值，也不會擋刪 `p001`。
2. **FK 只在新增時檢查。** 課堂用了兩段：新增子列要對得到；刪父列時若仍被參照也不准刪。只記其中一邊，另一邊仍會斷頭。
3. **被參照的欄隨便都能指。** 沒有 PK、也沒有 unique key，就不能被參照。唯一性是前提。
4. **外來鍵會把出版社的名稱、電話一併存進書表。** FK 只保證編號對得上。名稱和電話仍在出版社表。關聯是參照。
5. **所有對出版社表的刪除都會失敗。** 課堂的規則是「被人家參照到的那一筆」不能刪。沒有書指向的出版社，這堂課沒有說不能刪。把規則記成「父表鎖死不能刪」會過度限制。

## 9. Bug Hunt

找出問題、說明原因、提出修法。不要只改寫法風格。

### 題 1

```sql
CREATE TABLE publisher (
  publisher_id VARCHAR(10),
  name VARCHAR(50),
  phone VARCHAR(20)
);

CREATE TABLE book (
  book_id VARCHAR(10),
  title VARCHAR(100),
  publisher_id VARCHAR(10),
  CONSTRAINT fk_book_publisher
    FOREIGN KEY (publisher_id)
    REFERENCES publisher (publisher_id)
);
```

### 題 2

設計者的想法是：一本書屬於一家出版社，所以「出版社表應該記住它出了哪些書」。於是這樣建：

```sql
CREATE TABLE book (
  book_id VARCHAR(10) PRIMARY KEY,
  title VARCHAR(100)
);

CREATE TABLE publisher (
  publisher_id VARCHAR(10) PRIMARY KEY,
  name VARCHAR(50),
  book_id VARCHAR(10),
  CONSTRAINT fk_publisher_book
    FOREIGN KEY (book_id)
    REFERENCES book (book_id)
);
```

接著打算讓同一家出版社對應很多本書。

## 10. Coding Challenge

換一個場景：線上課程平台。學員要選課，之後寄課前通知時必須找得到這門課的老師聯絡方式。

**目標**（約 15–25 分鐘）

設計 `teacher` 與 `course` 兩張表的欄位與約束，讓資料庫自己守住「一門課屬於一位老師」。

**限制**

- 老師的識別必須能被課程參照。
- 課程表不要複製老師的姓名、電話；那些資料只存在老師表。
- 用本堂教過的規則思考這三件事，不必真的連上 MySQL，但要寫出你打算執行的新增／刪除例子：
  1. 新增一門課，老師編號在老師表裡存在。
  2. 新增一門課，老師編號在老師表裡不存在。
  3. 刪除一位「已有課程」的老師，以及刪除一位「還沒有課程」的老師。

**完成標準**

- 寫出兩張表各有哪些欄、誰是 PK、誰是 FK、FK 指向哪裡。
- 對上面三個操作，各寫「會成功或失敗」以及用斷頭資料的邏輯解釋原因。
- 寫出：若老師表的識別沒有唯一性，會怎樣。

**Stretch**

同一位老師可以開很多門課。說明你的 FK 方向為什麼允許這件事，以及如果把 FK 建在反方向，會怎樣限制「一位老師多門課」。

## 11. Retrieval Practice

**Why.** 書表明明「不該有」出版社編號，為什麼還是必須有這個欄位？沒有它，之後哪一件具體的事做不成？

**How.** 要把書的出版社 id 設成 FK，資料庫會先要求你做什麼？若出版社 id 既不是 PK 也不是 unique key，接下來會怎樣？

**Trade-off.** 被參照端用 PK 或用 unique key，課堂認為差別在哪？若兩邊都不設，代價是什麼？

**Prediction.** 出版社 `P001` 已被 *Head First Java* 參照。此時刪除 `P001`，以及新增一本出版社編號為 `P001` 的新書，這兩件事各會怎樣？內部各檢查了什麼？

**Application.** 若改成「訂單」與「客戶」：訂單要能聯絡到下單客戶。FK 應該建在哪一張表的哪一個欄？新增訂單、刪除客戶時，各要擋住哪一種斷頭？

## 12. 下一步

建議接著學的三個觀念，都接在本堂停住的地方：

1. **外來鍵的詳細設定。** 老師本堂明確留到後面。你現在只知道「有參照就不准刪父列」；詳細設定會決定刪／改時還能怎麼處理。
2. **真正把兩張表的資料一起查出來。** FK 只保證編號有效，不會把出版社名稱、電話自動出現在書的查詢結果裡。要訂購時把「頭」的資訊讀出來，需要關聯查詢。
3. **主鍵與唯一鍵在關聯裡的角色。** 本堂把兩者都當「可被參照的唯一性」。下一層是：一張表以哪個欄當穩定識別、哪個欄只是額外唯一，會影響 FK 該指向誰。

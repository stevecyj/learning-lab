# 12-2 建立外來鍵限制

> 本筆記以逐字稿為依據。逐字稿提到畫面上的 SQL 行號，卻沒有收錄完整程式碼；以下範例依課堂明確說明的 `book_table`、`publisher_table` 與 `publisher_id` 關係重建，不代表畫面原碼逐字轉錄。

## 1. 這堂課真正要解決的問題

這堂課要讓 `book_table` 裡的出版社編號，確實指向 `publisher_table` 中存在且可唯一辨認的一間出版社。

假設 `book_table.publisher_id` 只是一個普通欄位，資料庫不會知道它代表「出版社」。加入外來鍵（foreign key, FK）後，資料庫才會正式保存「書籍的出版社編號參照出版社表」這段關係。

> **延伸知識**：外來鍵的實際價值之一，是避免子表保存找不到對應父表資料的參照值。不過，本段逐字稿聚焦在「如何建立限制」與「為何建立失敗」，沒有示範新增、更新或刪除資料時的檢查行為。

本課建立的關係是：

```text
book_table.publisher_id
        │
        └──參照──> publisher_table.publisher_id
```

要成功建立這條外來鍵，必須符合三個條件：

1. 被參照欄位必須是主鍵，或其他具有唯一性的鍵。
2. 外來鍵與被參照欄位的資料型別最好一致，至少必須相容。
3. 自訂的限制名稱不能與其他限制名稱重複。

## 2. 核心概念

### 2.1 外來鍵是一條跨表的參照限制

外來鍵是某張表中的欄位，用來參照另一張表的指定欄位。例如一本書連到一間出版社，就可以把 `book_table.publisher_id` 設為外來鍵。

只把兩個欄位都命名為 `publisher_id`，資料庫不會自動理解它們的關係。建立外來鍵後，資料庫才會檢查書籍所填的出版社編號。若兩個欄位沒有真正的參照關係，就不該只因名稱或型別相似而把它們連起來。

### 2.2 被參照欄位必須能唯一辨認資料

外來鍵通常參照主鍵（primary key, PK），也能參照其他具有唯一性的鍵，例如 unique key（UK）。一個外來鍵值必須能明確指向一筆資料；若被參照欄位允許重複，同一個值就可能對上多筆資料。因此，被參照欄位必須由 PK 或唯一性限制保證不重複。

### 2.3 兩端的資料型別必須一致或相容

`book_table.publisher_id` 與 `publisher_table.publisher_id` 保存的是同一種識別值，資料庫必須能比較兩者，所以型別最好完全一致。若兩端沒有相容的型別，應先修正欄位設計，否則外來鍵可能建立失敗。

逐字稿指出，許多資料庫管理系統允許「不完全相同但相容」的型別，例如同屬文字型別、字數不同。不過老師仍建議型別最好一致。

### 2.4 限制名稱與外來鍵規則是兩件事

建立外來鍵不能少了 `FOREIGN KEY ... REFERENCES ...`。前面的 `CONSTRAINT 限制名稱` 則可省略。替限制命名後，名稱會出現在違反限制的錯誤訊息中，比較容易查出是哪條規則出問題。不需要控制名稱時，可以讓系統命名；自行命名時則不能與其他限制重複。

### 2.5 Workbench 與 SQL 是兩個建立入口

課堂示範兩種方式：

- 在 MySQL Workbench 的 `Foreign Keys` 頁籤中選擇外來鍵欄位、被參照表與被參照欄位，再按 `Apply`。
- 在 `CREATE TABLE` 中直接寫出外來鍵限制。

兩種方式最後都會建立同一條資料庫限制。Workbench 會在選定 `book_table.publisher_id` 後協助配對 `publisher_table.publisher_id`，但使用者仍要分清楚哪個欄位是外來鍵、它參照哪張表的哪個欄位。

## 3. Mental Model

先把兩張表分成「保存對象」與「引用對象」：

```text
父表：publisher_table
publisher_id 是 PK 或唯一鍵
          │
          │ 提供可被唯一辨認的出版社編號
          ▼
子表：book_table
publisher_id 是 FK
```

建立限制時，資料庫會處理以下資訊：

1. `book_table.publisher_id` 是要受到限制的欄位。
2. `REFERENCES publisher_table(publisher_id)` 指定它要參照的位置。
3. 資料庫檢查兩端型別是否一致或相容。
4. 資料庫檢查父表欄位是否由 PK 或唯一鍵保證唯一。
5. 若自訂限制名稱，也要確認名稱沒有重複。
6. 條件成立後，資料庫才建立這條跨表規則。

`book_table.publisher_id` 保存的是出版社編號，不是出版社的完整資料。外來鍵要求這個編號必須能對上 `publisher_table.publisher_id`。

## 4. 專家視角

### 初學者需要知道，但資深工程師通常不會特別思考的內容

- **分清楚 FK 欄位與被參照欄位**：`book_table.publisher_id` 是 FK；`publisher_table.publisher_id` 是它參照的欄位。兩者名稱碰巧相同，不代表角色相同。
- **`CONSTRAINT` 名稱不是外來鍵本身**：省略名稱仍能建立 FK；不能省略的是外來鍵與參照對象的定義。
- **Workbench 的自動配對不等於已建立關係**：按下 `Apply` 並成功建立限制後，資料庫才會保存這段關係。

### 即使是資深工程師仍然會注意的內容

- **型別設計**：即使系統接受相容但不完全相同的型別，一致的定義仍較容易理解與維護。逐字稿只說明「相容可能可接受」，沒有列出 MySQL 對所有型別組合的精確規則。
- **參照目標是否真的唯一**：欄位在業務意義上看似不重複還不夠；資料庫必須以 PK 或唯一鍵保證它。
- **限制名稱是否容易辨認**：有意義且不重複的名稱，能讓違反 FK 時的錯誤訊息直接指出出問題的關係。

## 5. 語法 vs 通用知識

### 語言特有知識

- MySQL 可在 `CREATE TABLE` 中使用 `FOREIGN KEY (...) REFERENCES ... (...)` 建立外來鍵。
- 可用 `CONSTRAINT 名稱` 自訂限制名稱。
- MySQL Workbench 提供 `Foreign Keys` 頁籤，以視覺方式選取外來鍵欄位、被參照表與欄位。
- 逐字稿示範了查詢 `bookshop` 資料庫中 `book_table` 參照資訊的 SQL，但字幕未保留完整指令，因此無法準確重現。

### 通用程式設計知識

- **參照完整性**：由資料庫限制檢查資料之間的關係，而不是只靠人或應用程式記得。
- **唯一識別**：一個參照必須能明確找到唯一對象。這與程式中用唯一 ID 找物件、用唯一鍵找快取項目的想法相通。
- **介面契約一致**：關係兩端的資料型別要能對接，類似函式提供的值必須符合參數預期型別。
- **可診斷的命名**：規則名稱出現在錯誤訊息中；清楚命名能縮短除錯時間。

## 6. Trade-off

### Workbench 視覺操作 vs 直接寫 SQL

| 比較 | Workbench | SQL |
| --- | --- | --- |
| 建立方式 | 在頁籤中選表與欄位，再套用 | 明確寫出 `FOREIGN KEY` 與 `REFERENCES` |
| 優點 | 可視化，容易看見可選的表與欄位；會協助配對 | 關係定義直接呈現在程式碼中 |
| 成本 | 介面會代替使用者產生部分設定，較難直接看出完整 SQL | 必須分清楚 FK 欄位、父表及被參照欄位 |
| 適合情境 | 初次探索資料表結構、用圖形介面建立表格 | 需要直接用指令建立表格及限制 |
| 選錯的後果 | 選錯表或欄位，會建立錯誤關係或建立失敗 | 寫錯欄位、型別或參照對象，同樣會失敗 |

### 自訂限制名稱 vs 不自訂名稱

| 比較 | 自訂名稱 | 不自訂名稱 |
| --- | --- | --- |
| 優點 | 錯誤訊息較容易辨認是哪條 FK | SQL 少一段可省略的宣告 |
| 成本 | 必須命名且不能與其他限制重複 | 系統顯示的名稱可能較不直觀 |
| 適合情境 | 重視維護與除錯辨識 | 不需要控制名稱 |

## 7. 常見誤解

1. **「欄位叫 `publisher_id`，資料庫就知道它們有關係。」** 只有明確建立 FK 後，資料庫才保存並檢查這段關係。
2. **「外來鍵只能參照主鍵。」** 逐字稿說明也可以參照其他具有唯一性的鍵。
3. **「任意普通欄位都能被參照。」** 被參照欄位不能保存重複值，必須具備唯一性。
4. **「只要值看起來一樣，欄位型別就不重要。」** 建立 FK 時，兩端型別最好一致，至少要相容，否則可能失敗。
5. **「省略 `CONSTRAINT` 名稱就等於沒有外來鍵。」** 名稱可省略；`FOREIGN KEY ... REFERENCES ...` 才是限制的核心。


## 10. Coding Challenge

### 情境：訂單與顧客

在 10～30 分鐘內建立 `customer_table` 與 `order_table`，讓每筆訂單能參照一位顧客。

**目標**

- `customer_table` 有一個能唯一辨認顧客的 `customer_id`。
- `order_table` 有自己的主鍵，並以 `customer_id` 參照顧客表。
- 替外來鍵限制取一個能看出兩張表關係的名稱。

**限制**

- 兩端的 `customer_id` 使用一致的資料型別。
- 被參照的 `customer_table.customer_id` 必須由資料庫保證唯一。
- 使用一段 `CREATE TABLE` SQL 建立每張表；先建立被參照的表。

**完成標準**

- 兩張表都能成功建立。
- 能指出哪個欄位是 FK、它參照哪個表的哪個欄位。
- 能說明為何被參照欄位可作為明確的參照對象。
- 能說明自訂限制名稱在除錯時的用途。

**延伸挑戰（選做）**

改用一個不是主鍵、但具有唯一性的顧客欄位作為參照目標，並說明為何仍符合本課規則。

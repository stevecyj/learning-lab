# 認識數字類型 (Numeric Data Types)

說明 MySQL 的三種數字類型：整數（含 `UNSIGNED`）、浮點數（`DOUBLE`）與自訂精準度定點數（`DECIMAL`），並比較它們的儲存方式、數值範圍與適用場景。

---

## 1. 這堂課真正要解決的問題

資料庫中的數值資料有不同需求：編號與數量不需要小數，科學量測容許微小誤差，而交易金額則要求每一位數都完全精確。

若型別選擇不當，會產生以下問題：
1. **浮點數精度誤差**：用 `DOUBLE` 存金額時，二進位浮點運算的近似值會讓帳目加總出現微小偏差。
2. **數值範圍浪費或溢位**：主鍵 ID 不會有負數，若使用預設的 `SIGNED` 整數，會浪費一半的正整數編號空間；若選用範圍太小的型別（如 `TINYINT`），資料增加時容易溢位。
3. **位數約束不足**：未依業務規範限制小數與整數位數，會讓超出範圍的資料寫入資料庫。

本課的核心在於釐清「無小數（整數）」、「系統預設精度小數（`DOUBLE`）」與「自訂精度小數（`DECIMAL`）」的差異，並在欄位定義時正確配置範圍與精度。

---

## 2. 核心概念

### 概念一：整數類型與無符號屬性 (Integer & `UNSIGNED`)
- **它是什麼**：儲存不帶小數的整數（如 `INT`、`TINYINT`），可搭配 `UNSIGNED` 屬性（MySQL Workbench 縮寫為 `UN`）。
- **為什麼存在**：以固定位元組儲存整數，兼顧查詢效率與儲存空間。
- **解決什麼問題**：
  - 避免純整數因使用浮點數或字串而浪費空間與索引效能。
  - 透過 `UNSIGNED` 將負數區間轉移給正數，使正整數可用上限翻倍（例如 `TINYINT` 有符號為 `-128 ~ 127`，無符號為 `0 ~ 255`）。
- **何時使用**：主鍵 ID、流水號、年齡、商品數量等非負整數。
- **何時不適合使用**：數值可能為負數的情境（如溫標、帳戶增減變動量、座標位移）。

### 概念二：浮點數類型 (`DOUBLE` / Floating-Point)
- **它是什麼**：儲存帶有小數的數值，其精準度由系統底層標準決定，使用者無法手動調整小數位數的內部編碼。
- **為什麼存在**：在固定位元組內以科學記號法表示極大或極小的小數。
- **解決什麼問題**：滿足科學計算與物理量測對寬廣數值範圍與高速硬體運算的需求。
- **何時使用**：容許微小近似誤差的場景（如感測器數據、概略百分比、科學數據）。
- **何時不適合使用**：訂單金額、帳戶餘額、稅率等不允許任何近似誤差的財務資料。

### 概念三：自訂精準度定點數類型 (`DECIMAL(M, D)`)
- **它是什麼**：由開發者自訂總位數與小數位數的精確數值型別，語法為 `DECIMAL(M, D)`。
  - `M`（Precision）：總位數（整數位數 + 小數位數）。例如 `DECIMAL(8, 2)` 總共可存 8 位數。
  - `D`（Scale）：小數位數。例如 `DECIMAL(8, 2)` 小數佔 2 位。
  - 整數位數：由公式 `M - D` 計算（在 `DECIMAL(8, 2)` 中，整數最多佔 `8 - 2 = 6` 位）。
- **為什麼存在**：浮點數以二進位儲存時會有微小近似誤差，定點數則以十進位方式精確儲存每一位數字。
- **解決什麼問題**：消除小數運算的精度遺失，並限制欄位的整數與小數長度。
- **何時使用**：商品單價、結算金額、匯率、稅率等財務數據。
- **何時不適合使用**：不含小數的數值（應使用 `INT`），或範圍極廣且容許誤差的科學計算（使用浮點數運算更快且更省空間）。

## 3. Mental Model

### 1. 有符號 (`SIGNED`) vs 無符號 (`UNSIGNED`) 空間分配

整數欄位的二進位總容量固定。以 8 位元的 `TINYINT`（共 256 個可能值）為例：

```
預設 SIGNED (有符號):
[-128 ------------------- 0 ------------------- 127]
 <──── 負數佔一半 ────>     <──── 正數佔一半 ────>
 (用於主鍵 ID 時，負數範圍無法利用)

啟用 UNSIGNED (無符號):
[0 -------------------------------------------- 255]
 <────────────── 全部容量提供給正數 ──────────────>
 (正數上限翻倍，不浪費編號容量)
```

---

### 2. `DECIMAL(M, D)` 的位數拆解

以 `DECIMAL(8, 2)` 為例，總位數 `M = 8`，小數位數 `D = 2`：

```
                    ┌───────────────────────────────┐
                    │     DECIMAL(8, 2) 總位數: 8    │
                    └───────────────┬───────────────┘
                                    │
            ┌───────────────────────┴───────────────────────┐
            ▼                                               ▼
┌───────────────────────┐                       ┌───────────────────────┐
│  整數部分 (M - D = 6)  │       [ 小數點 . ]     │    小數部分 (D = 2)   │
│     9 9 9 9 9 9       │           .           │          9 9          │
└───────────────────────┘                       └───────────────────────┘
  (最大正值: 999999.99，整數最多 6 位，小數保留 2 位)
```

---

### 3. `DOUBLE` (浮點數) vs `DECIMAL` (定點數) 儲存機制

```
儲存數值 0.1:

[ DOUBLE (二進位近似值) ]
二進位無法精確表示 0.1 ──► 0.0001100110011... ──► 內部值: 0.10000000000000000555...
(多次運算容易累積誤差)

[ DECIMAL(4, 2) (十進位精準儲存) ]
十進位數值對齊儲存 ──► 整數: 00, 小數: 10 ──► 內部值: 0.10
(運算結果精準，無二進位轉換誤差)
```

## 4. 專家視角

### 初學者需要知道，但資深工程師通常不會特別思考的內容
1. **Workbench 的 `UN` 代表 `UNSIGNED`**：在 MySQL Workbench 欄位設定中，勾選 `UN` 即為無符號整數。
2. **`DECIMAL(M, D)` 的 `M` 是總位數而非整數位數**：`DECIMAL(8, 2)` 的整數位數上限為 `8 - 2 = 6` 位，能儲存的最大值是 `999999.99`。
3. **整數欄位不會自動保留小數**：將小數寫入 `INT` 欄位時，小數會被捨去或四捨五入（依 SQL Mode 決定），不會自動把欄位轉換為浮點數。

### 即使是資深工程師仍然會注意的內容
1. **金額欄位使用 `DECIMAL` 或最小整數單位**：涉及財務計算的金額必須使用 `DECIMAL`，或以最小單位（例如「分」或 cents）使用 `BIGINT/INT` 儲存，避免浮點累積誤差（*延伸知識*）。
2. **主鍵與外鍵的型別與符號必須一致**：若主表主鍵為 `INT UNSIGNED`，關聯表的外鍵欄位也必須設為 `INT UNSIGNED`，否則建立外鍵約束時會報錯，且可能影響關聯查詢的索引效能（*延伸知識*）。
3. **預留業務增長空間**：宣告 `DECIMAL(M, D)` 時需預估長期業務量。例如 `DECIMAL(8, 2)` 上限為 `999,999.99`（不到百萬），若金額超過該上限，寫入時會觸發 `Numeric value out of range` 錯誤。

| 分類 | 具體內容 | 通用程式設計對應觀念 |
| :--- | :--- | :--- |
| **MySQL 語法與工具** | Workbench 勾選 `UN`<br>`INT UNSIGNED`<br>`DECIMAL(M, D)` | 資料定義語言（DDL）中的數值型別與符號約束宣告。 |
| **通用觀念** | **無符號整數 (Unsigned Integer)** | 在 C/C++、Rust、Go 中的 `uint32` / `uint64`，將符號位元轉為數值位元使正數上限加倍。 |
| **通用觀念** | **IEEE 754 浮點數精度限制** | JavaScript 的 `Number`、Python 的 `float` 與 MySQL `DOUBLE` 皆採二進位浮點儲存，存在小數精度誤差。 |
| **通用觀念** | **定點數 (Fixed-point / Decimal)** | 對應 Python 的 `decimal.Decimal`、Java 的 `BigDecimal`、C# 的 `decimal`，用於高精度計算。 |
| **通用觀念** | **Schema 層級型別約束** | 在資料庫底層限制資料格式與長度，防止非法數據寫入。 |

## 6. Trade-off

### 1. `INT (SIGNED)` vs `INT UNSIGNED`

| 比較維度 | `INT` (預設有符號) | `INT UNSIGNED` (無符號) |
| :--- | :--- | :--- |
| **數值範圍** | `-2,147,483,648 ~ 2,147,483,647` | `0 ~ 4,294,967,295` |
| **正數容量** | 約 21.4 億 | 約 42.9 億（容量加倍） |
| **負數支援** | 支援 | 不支援（寫入負數會報錯或警告） |
| **適用場景** | 溫度、差額、盈虧、座標位移 | 主鍵 ID、計數器、庫存、年齡 |
| **選錯後果** | 用於流水號 ID 時，浪費一半（約 21 億）的可用編號 | 用於可能出現負數的欄位時，會發生溢位或寫入失敗 |

---

### 2. `DOUBLE` (浮點數) vs `DECIMAL(M, D)` (定點數)

| 比較維度 | `DOUBLE` (浮點數) | `DECIMAL(M, D)` (自訂精準度定點數) |
| :--- | :--- | :--- |
| **精確度** | 近似值（不可自訂小數位數，底層二進位儲存） | 絕對精確（由開發者自訂總位數與小數位數） |
| **運算效能** | 高（使用 CPU 硬體浮點運算） | 較低（由資料庫軟體層模擬十進位運算） |
| **儲存空間** | 固定 8 位元組 | 依 `M` 與 `D` 長度動態分配位元組（*延伸知識*） |
| **適用場景** | 科學計算、物理量測、地理座標（概略） | 貨幣金額、交易結算、發票稅額、會計帳目 |
| **選錯後果** | 用於財務計算會累積四捨五入誤差，導致帳目對不齊 | 用於大量科學計算時，運算耗時與儲存空間增加 |

## 7. 常見誤解

### 誤解一：`DECIMAL(8, 2)` 代表整數可以存 8 位、小數存 2 位，總共可以存 10 位數？
> **事實**：`M`（8）代表**總位數**。整數位數上限為 `M - D = 8 - 2 = 6` 位，因此最大值為 `999,999.99`。若輸入整數 7 位（如 `1234567.89`），寫入時會超出範圍報錯。

### 誤解二：計算金額用 `DOUBLE` 比較快，只要在顯示時四捨五入即可？
> **事實**：浮點數在多次運算後會累積微小誤差，導致明細加總與總額不符（例如 `0.1 + 0.2` 不等於 `0.3`），在財務系統中不能依賴顯示層的四捨五入來解決。

### 誤解三：主鍵 ID 只是單純編號，使用預設的 `INT` 即可，不需要設定 `UNSIGNED`？
> **事實**：主鍵 ID 通常由 1 開始遞增且不為負數。預設 `INT` 僅提供約 21 億筆正整數，改用 `UNSIGNED` 可以在相同空間內將可用容量提升至約 43 億筆。

### 誤解四：欄位型別設為 `INT` 後，寫入 `99.8` 時資料庫會自動將欄位改為浮點數儲存？
> **事實**：MySQL 欄位型別在建立後固定。寫入小數至 `INT` 欄位時，小數部分會直接被捨去或四捨五入為整數，不會動態更改欄位定義。

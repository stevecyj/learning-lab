# 認識日期時間類型

## 1. 這堂課真正要解決的問題

這堂課要處理兩件事：根據資料的用途選擇 `DATE`、`DATETIME` 或 `TIMESTAMP`，以及設定 MySQL 自動記錄資料的新增與修改時間。

- 只需要年月日，例如出版日期：使用 `DATE`。
- 需要年月日時分秒，而且不希望 MySQL 根據時區轉換：使用 `DATETIME`。
- 需要完整時間，並希望 MySQL 以 UTC 為基礎儲存：使用 `TIMESTAMP`。

型別選錯時，欄位可能保存不需要的資訊，也可能讓人誤判時間的意義。例如，出版日期不需要時分秒；`DATETIME` 也不會像 `TIMESTAMP` 一樣轉成 UTC。

MySQL 提供以下設定，自動維護新增與修改時間：

```sql
DEFAULT CURRENT_TIMESTAMP
ON UPDATE CURRENT_TIMESTAMP
```

這樣可以降低應用程式漏填時間的機會。

---

## 2. 核心概念

### 概念一：`DATE` 表示日曆上的某一天

`DATE` 儲存年月日，不包含時、分、秒。概念上的格式是：

```text
YYYY-MM-DD
```

逐字稿以書籍出版日期為例：

```sql
publication_date DATE
```

這個欄位只需要表達「哪一天出版」。如果還要知道當天的具體時刻，`DATE` 就不適合。

### 概念二：`DATETIME` 保存完整日期時間，但不處理時區

`DATETIME` 可以儲存年、月、日、時、分、秒，概念上的格式是：

```text
YYYY-MM-DD HH:MM:SS
```

按照逐字稿的說明，`DATETIME` 不會把時間轉換成 UTC，而是保存輸入的年月日時分秒。需要完整時間，但不希望 MySQL 根據時區轉換時，可以使用它。

### 概念三：`TIMESTAMP` 會以 UTC 為基礎儲存時間

`TIMESTAMP` 也能表示年月日時分秒，但逐字稿指出，它會把日期時間轉換成 UTC 後儲存，而且支援的日期區間不像 `DATETIME` 那麼廣。

本課將它搭配自動新增與修改時間使用，適合記錄資料何時建立或更新。

### 概念四：新增時自動填入目前時間

欄位設定：

```sql
DEFAULT CURRENT_TIMESTAMP
```

代表新增資料時，如果沒有提供這個欄位的值，MySQL 就使用新增當下的系統時間。

### 概念五：修改時自動更新時間

欄位再加上：

```sql
ON UPDATE CURRENT_TIMESTAMP
```

代表之後修改這筆資料時，MySQL 會把欄位更新成修改當下的時間。完整定義例如：

```sql
updated_at TIMESTAMP
    DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP
```

兩個設定分別處理新增和修改：

- `DEFAULT CURRENT_TIMESTAMP`：新增時自動填入。
- `ON UPDATE CURRENT_TIMESTAMP`：修改時自動更新。

如果欄位代表永遠不應改變的原始建立時間，就不適合加上 `ON UPDATE CURRENT_TIMESTAMP`。

### DataGrip 圖形介面產生的 SQL

課堂在 MySQL Workbench 的圖形介面中建立日期時間練習表，欄位設定如下：

- `publication_date DATE`
- `datetime DATETIME`
- `timestamp TIMESTAMP`
- `timestamp` 新增時自動填入目前時間，修改時也自動更新

逐字稿有講到這組欄位設計，但沒有直接展示完整的 `CREATE TABLE` 指令。以下是使用 DataGrip 的 SQL Script Generator，依照相同設定產生的 DDL：

```sql
CREATE TABLE date_time
(
    publication_date DATE                                NULL,
    datetime         DATETIME                            NULL,
    timestamp        TIMESTAMP DEFAULT CURRENT_TIMESTAMP NULL ON UPDATE CURRENT_TIMESTAMP
);
```

執行這段 SQL 後，MySQL 會：

1. 建立名為 `date_time` 的資料表。
2. 建立只儲存日期的 `publication_date`。
3. 建立儲存完整日期時間的 `datetime`。
4. 建立 `timestamp`；新增時若省略它，就使用目前時間，修改資料時再自動更新。

三個欄位後面的 `NULL` 表示允許保存 SQL 的 `NULL`，也就是「沒有值」，它和字串 `'NULL'` 不同。

DataGrip 為了對齊內容加入較多空格，空格不會改變執行結果。較容易閱讀的寫法是：

```sql
CREATE TABLE date_time (
    publication_date DATE NULL,
    datetime DATETIME NULL,
    timestamp TIMESTAMP
        DEFAULT CURRENT_TIMESTAMP
        NULL
        ON UPDATE CURRENT_TIMESTAMP
);
```

課堂使用 MySQL Workbench。在 Workbench 的 `Default` 輸入欄位中，只要填入：

```text
CURRENT_TIMESTAMP
```

因為輸入框本身已代表 `DEFAULT`。DataGrip 的 SQL Script Generator 則會還原成完整 SQL：

```sql
DEFAULT CURRENT_TIMESTAMP
```

兩套軟體的畫面不同，送給 MySQL Server 的資料表定義相同。

## 3. Mental Model

先判斷資料要保存到多精確：

```text
只需要年月日
    ↓
   DATE

需要年月日時分秒
    ↓
是否需要課堂所述的 UTC 轉換？
    ├─ 否 → DATETIME
    └─ 是 → TIMESTAMP
```

選好型別後，再決定時間何時產生：

```text
INSERT 時沒有提供時間
    ↓
DEFAULT CURRENT_TIMESTAMP
    ↓
MySQL 填入新增當下的時間

UPDATE 修改資料
    ↓
ON UPDATE CURRENT_TIMESTAMP
    ↓
MySQL 改成修改當下的時間
```

資料型別決定「如何表示時間」；`DEFAULT` 和 `ON UPDATE` 決定「何時自動產生時間值」。

## 4. 專家視角

### 初學者需要知道，但資深工程師通常不會特別思考的內容

完整 SQL 和 GUI 欄位的寫法不同。SQL 要寫 `DEFAULT CURRENT_TIMESTAMP`，Workbench 的 Default 欄位只填 `CURRENT_TIMESTAMP`。

新增和修改也是兩個時機。只有 `DEFAULT CURRENT_TIMESTAMP` 不代表修改時會更新，還需要 `ON UPDATE CURRENT_TIMESTAMP`。

`NULL` 代表沒有值，不是文字，也不是空字串。

### 即使是資深工程師仍然會注意的內容

欄位型別要符合資料語意。出版日期只需要年月日，使用 `DATE` 比完整時間更準確。

`DATETIME` 與 `TIMESTAMP` 看起來相似，但逐字稿指出兩者對 UTC 的處理不同。資料可能包含很早或很晚的日期時，還要檢查型別的支援範圍。

## 5. 語法 vs 通用知識

### MySQL 特有知識

```sql
DATE
DATETIME
TIMESTAMP
DEFAULT CURRENT_TIMESTAMP
ON UPDATE CURRENT_TIMESTAMP
```

Workbench 的 Default 欄位只填 `CURRENT_TIMESTAMP`，則是特定工具的操作方式。

### 通用程式設計知識

出版日期和最後修改時刻都是時間資料，但代表不同概念。用型別表達資料意義，可以避免只因為兩者都能寫成日期字串，就採用相同的儲存方式。

預設值處理資料建立時的初始狀態，更新規則則處理之後的變化。讓資料庫自動填入時間，也能降低不同程式漏填的機會。

## 6. Trade-off

### `DATE` vs `DATETIME`

| 比較 | `DATE` | `DATETIME` |
| --- | --- | --- |
| 保存內容 | 年月日 | 年月日時分秒 |
| 優點 | 語意清楚 | 可以保存具體時刻 |
| 成本 | 無法表示時分秒 | 可能保存不需要的資訊 |
| 適合情境 | 出版日期 | 需要完整日期時間 |

### `DATETIME` vs `TIMESTAMP`

| 比較 | `DATETIME` | `TIMESTAMP` |
| --- | --- | --- |
| UTC 處理 | 不轉成 UTC | 轉成 UTC 儲存 |
| 支援範圍 | 逐字稿指出較廣 | 逐字稿指出較窄 |
| 適合情境 | 保存輸入的時間本身 | 需要 UTC 轉換概念的時間 |

### 手動填時間 vs MySQL 自動填時間

| 比較 | 手動提供 | `CURRENT_TIMESTAMP` 自動填入 |
| --- | --- | --- |
| 控制權 | 呼叫端決定時間 | MySQL 使用當下時間 |
| 優點 | 可以指定時間 | 不容易漏填 |
| 成本 | 每次都必須正確提供 | 不適合必須由外部指定的時間 |

手動填入與自動填入的取捨屬於延伸分析；逐字稿示範的是 MySQL 自動填入。

---

## 7. 常見誤解

1. `DATETIME` 和 `TIMESTAMP` 只是名稱不同。兩者對 UTC 的處理方式和支援範圍不同。
2. 日期資料一律使用 `DATETIME`。出版日期只需要年月日，`DATE` 更符合語意。
3. 設定 `DEFAULT CURRENT_TIMESTAMP` 後，修改資料也會更新時間。修改時還需要 `ON UPDATE CURRENT_TIMESTAMP`。
4. Workbench 的 Default 欄位要輸入完整的 `DEFAULT CURRENT_TIMESTAMP`。該欄位只需輸入 `CURRENT_TIMESTAMP`。
5. 超過型別支援範圍也一定正確。逐字稿說可能仍可處理，但不保證不出錯，可能有精準度問題。

## 10. Coding Challenge

### 欄位需求

- `title`：教材名稱。
- `release_date`：教材發布日期，只需要年月日。
- `scheduled_at`：預定上線的完整日期時間，不使用本課所述的 UTC 轉換。

### 限制

- 從 `DATE`、`DATETIME`、`TIMESTAMP` 選擇型別。

# 瞭解表格設計流程

說明如何從業務需求與紙本單據推導欄位，透過正規化拆分表格消除重複，最後在 MySQL 中建立資料表與關聯。

---

## 1. 這堂課真正要解決的問題

建立資料庫表格不能靠憑空想像，也不該直接把所有資訊塞進同一張包山包海的大表。

未經規劃就直接建表，常見兩大問題：
1. **漏掉關鍵欄位**：沒有看過業務現場，系統上線後才發現缺資料（例如有商品卻沒有倉儲架位編號）。
2. **資料大量重複與異常**：把不同實體的資訊（如書籍與出版社）混在同張表，同一家出版社出了多本書，出版社資料就會重複出現；一旦出版社改電話或搬家，容易漏改而造成資料矛盾。

標準的表格設計流程分為四步：從業務現場收集資料、整理初步欄位、透過正規化拆分表格，最後在 MySQL 中建立資料表與關聯。

---

## 2. 核心概念

### 概念一：業務導向的資料需求收集
- **它是什麼**：透過訪談使用者、收集紙本單據與實地觀察現場，確認系統必須儲存哪些資料欄位。
- **為什麼存在**：資料庫是為了支援業務運作，只有從實際流程中才能找出完整且真實的欄位需求。
- **解決什麼問題**：避免遺漏必要欄位或選錯資料型態。
- **何時使用**：新專案啟動、規劃新功能或系統重構時。
- **何時不適合使用**：單純練習 SQL 語法或驗證演算法時，直接使用模擬資料即可，不需要做現場訪談。

### 概念二：資料庫正規化與消除重複 (Normalization)
- **它是什麼**：把包含多種實體資訊的大表，拆解成數個職責單一的小表，消除重複資料。
- **為什麼存在**：多筆資料共享相同屬性時（例如多本書屬於同一家出版社），放在同張表會造成出版社聯絡人與地址反覆出現，浪費空間且修改時容易漏改。
- **解決什麼問題**：避免重複儲存相同的文字，並防止修改時因漏改產生的資料矛盾（更新異常）。
- **何時使用**：整理出初步欄位後，發現某組欄位會隨多筆記錄反覆重複時。
- **何時不適合使用**：報表統計或資料倉儲（OLAP）為了查詢效能，有時會刻意保留重複欄位以減少跨表 JOIN（*反正規化，延伸知識*）。

### 概念三：實體落地與鍵值關聯 (PK & FK)
- **它是什麼**：在 MySQL 中建立實體表格、指定欄位型態，並透過主鍵（Primary Key）與外鍵（Foreign Key）建立表格間的關聯。
- **為什麼存在**：表格拆開後，必須有明確的連結方式，才能把分散的資料重新拼裝查詢。
- **解決什麼問題**：確保子表引用的父表資料真實存在，維護資料關聯的正確性。
- **何時使用**：完成正規化拆表，準備在 MySQL 中執行建表語法（DDL）時。
- **何時不適合使用**：使用非關聯式資料庫（如 MongoDB 或 Redis）時，通常改用內嵌結構或由應用程式代碼維護，不強制建立外鍵約束（*延伸知識*）。

## 3. Mental Model

### 表格設計的四階段轉化流程

```
[ 階段 1：業務資料收集 ]
   ├── 訪談使用者（如：書店需要管理圖書、定價、出版社）
   ├── 收集紙本單據（如：進出倉單據、送貨單）
   └── 現場實地觀察（如：倉庫架位標籤、商品編號、有效日期）
         │
         ▼
[ 階段 2：整理初步欄位（草稿大表） ]
   └── 書籍表：ISBN、書名、定價、作者、出版社名稱、聯絡人、電話、地址
         │
         ▼ (發現：多本書屬於同出版社，導致出版社資料重複出現)
[ 階段 3：資料庫正規化（拆分表格） ]
   ├── 表格 A【書籍表】：ISBN (PK)、書名、定價、作者、出版社編號 (FK)
   └── 表格 B【出版社表】：出版社編號 (PK)、出版社名稱、聯絡人、電話、地址
         │
         ▼
[ 階段 4：資料庫實體建置 (MySQL) ]
   ├── 建立 Database / Schema
   ├── 建立 Tables 並指定欄位型態 (VARCHAR, INT, DATE 等)
   └── 設定主鍵 (PK) 與外鍵 (FK) 關聯約束
```

## 4. 專家視角

### 初學者需要知道，但資深工程師通常不會特別思考的內容
1. **欄位不是憑空猜出來的**：看單據、問使用者、看現場標籤就能找出真實欄位。
2. **單一大表不是好設計**：把出版社資訊重複寫在每本書上看似直覺，後續維護會非常麻煩。
3. **設計順序不能顛倒**：先確認業務欄位，再做正規化拆表，最後才進 MySQL 執行建表語法。

### 即使是資深工程師仍然會注意的內容
1. **正規化與查詢效能的平衡**：交易系統（OLTP）嚴格遵守正規化以防止資料錯亂；資料倉儲或報表查詢（OLAP）則會在效能受限時評估反正規化（*延伸知識*）。
2. **實體關係的基數（Cardinality）**：一本書是否可能有「多位作者」？出版社是否可能有多個聯絡地址？設計初期就要確認是一對多還是多對多。
3. **欄位型態與長度的精確度**：根據業務特性選擇合適型態（例如定價用數值型態而非字串、日期用 DATE），避免浪費儲存空間與影響查詢效能。

## 5. 語法 vs 通用知識

| 分類 | 具體內容 | 通用程式設計對應觀念 |
| :--- | :--- | :--- |
| **MySQL / SQL 實作** | `CREATE TABLE`、欄位型態（`INT`, `VARCHAR`, `DATE`）、`PRIMARY KEY`、`FOREIGN KEY` | 特定關聯式資料庫管理系統（RDBMS）的資料定義語言（DDL）。 |
| **通用觀念** | **領域需求分析 (Domain Analysis)** | 軟體架構始於對現實業務流程的深入理解與資訊收集。 |
| **通用觀念** | **單一職責原則 (Single Responsibility)** | 一張表只負責描述單一實體（書籍表只管書，出版社表只管出版社）。 |
| **通用觀念** | **資料正規化 (Normalization)** | 消除冗餘資料，確保每一份事實只有單一來源（Single Source of Truth）。 |
| **通用觀念** | **實體關聯模型 (Entity-Relationship)** | 透過唯一識別碼（PK/FK）建立物件之間的連結與參照完整性。 |

## 6. Trade-off

### 比較：單一大表 vs 正規化多表

| 比較項目 | 單一大表 (未正規化 Flat Table) | 正規化多表 (Relational Tables) |
| :--- | :--- | :--- |
| **資料重複性** | 高（出版社資訊隨書籍反覆出現） | 極低（出版社資訊只存一次） |
| **資料修改** | 困難（改電話需更新幾百筆資料，容易遺漏） | 容易（只改出版社表的一筆資料，全系統即時同步） |
| **查詢方式** | 單表查詢，不需 JOIN | 查詢完整資料需使用 `JOIN` 串接多張表 |
| **儲存空間** | 浪費（重複文字佔用硬碟） | 精簡（只存關聯 ID） |
| **適用情境** | 臨時性資料匯出、簡單扁平試算表 | 正式資料庫系統、高頻更新的商業交易系統 |

## 7. 常見誤解

### 誤解一：設計資料庫的第一步，就是打開 MySQL Workbench 開始寫 `CREATE TABLE`？
> **事實**：直接建表容易遺漏欄位或造成結構混亂。正確的第一步是收集業務單據與現場標籤，列出欄位清單並完成正規化拆表後，才進系統建表。

### 誤解二：把所有欄位（書名、作者、出版社資訊）通通放在同一張表最方便，不用寫 JOIN 所以更好？
> **事實**：這會造成嚴重的資料重複。一旦出版社改電話，必須逐筆更新每本書的記錄；若有任何一筆漏改，就會導致同一家出版社出現兩種電話的矛盾狀態。

### 誤解三：正規化就是把表格切得越細越碎越好？
> **事實**：正規化是依據資料相依性消除「重複與異常」，不是盲目拆表。過度拆分會造成查詢時需要過多無謂的 `JOIN`，反而增加系統負擔。

### 誤解四：只要欄位名稱取對，資料型態全部用字串（VARCHAR）也沒關係？
> **事實**：了解存什麼資料就能推導出正確型態（如定價用數值、日期用 DATE）。全用字串會導致無法進行數值計算、大小比較與日期排序，且浪費儲存空間。

## 8. Code Prediction — 請先作答

閱讀以下情境與 SQL 邏輯，預測：
1. **執行結果 / 資料狀態**
2. **原因**
3. **系統內部發生的問題或機制**

### 題目一
```sql
-- 表格：books (未正規化大表)
-- 欄位：book_id, title, publisher_name, publisher_phone
-- 目前有 100 筆資料的 publisher_name 皆為 '大秦出版社'，舊電話為 '02-1234-5678'

UPDATE books 
SET publisher_phone = '02-8765-4321' 
WHERE title = 'MySQL 實戰指南';
```
> **問題**：執行完畢後，查詢其他 99 本「大秦出版社」的書籍，其 `publisher_phone` 會顯示什麼？這反映了未正規化大表的什麼問題？

### 題目二
```sql
-- 正規化架構：
-- 表格 1: publishers (publisher_id PK, publisher_name, publisher_phone)
-- 表格 2: books (book_id PK, title, publisher_id FK)
-- 目前有 100 本書關聯到 publisher_id = 1 ('大秦出版社')

UPDATE publishers 
SET publisher_phone = '02-8765-4321' 
WHERE publisher_id = 1;
```
> **問題**：
> 1. 這條更新語句修改了幾筆資料？
> 2. 此時透過關聯查詢這 100 本書的出版社電話，結果分別為何？為什麼？

### 題目三
```sql
-- 倉儲系統設計
-- 表格：warehouse_stock
-- 欄位：item_id, item_name, quantity
```
> **問題**：倉庫人員接到揀貨通知要去拿商品 `item_id = 'A101'`，他在系統中查詢該筆資料。系統能告訴他該去哪一個貨架拿貨嗎？這說明了資料收集階段（實地看架位標籤）的什麼重要性？

## 10. Coding Challenge

### 目標：從業務單據完成資料表正規化設計
某倉儲物流公司的「出入庫單據」包含以下欄位資訊：

```
單據編號, 單據日期, 單據類型 (進貨/出貨), 倉庫儲位 (架位編號),
商品編號, 商品名稱, 數量, 製造日期, 有效期限, 經辦員工編號, 經辦員工姓名
```

### 任務要求：
1. **實體識別**：分析上述單據中包含哪幾種獨立的業務實體（Entity）。
2. **表格拆分**：將這張原始大單據拆解為至少 3 張正規化表格，並列出各表的欄位。
3. **關聯設定**：為每張表格標註主鍵（PK）與外鍵（FK）。

### 完成標準：
- 商品名稱不隨單據明細重複儲存。
- 員工姓名不隨單據明細重複儲存。
- 主鍵與外鍵參照關係清楚合理。

### 挑戰延伸 (Stretch Goal)：
- 為各表格的欄位指定適合的 MySQL 資料型態（如 `INT`, `VARCHAR(n)`, `DATE` 等）。

## 12. 下一步

### 學完應掌握的技能：
- 掌握從業務需求、紙本單據、現場觀察萃取欄位的方法。
- 理解單一大表的弊病與正規化拆分的核心邏輯。
- 清楚資料庫設計的完整流程（需求收集 -> 整理欄位 -> 正規化拆表 -> 建立實體資料庫與 PK/FK）。

### 接續學習概念：
1. **資料型態精準選用 (`INT`, `VARCHAR`, `DECIMAL`, `DATE` 等)**：依據欄位內容特性選擇最佳儲存類型與長度。
2. **主鍵與外鍵語法實作 (`PRIMARY KEY` / `FOREIGN KEY ... REFERENCES`)**：在 MySQL 中撰寫 DDL 建立實體約束。
3. **多表關聯查詢語法 (`JOIN`)**：將拆分後的正規化表格透過 SQL 重新組裝查詢出完整業務資訊。

# 11-5 認識二位元資料

## 1. 這堂課真正要解決的問題

這堂課要解決的問題是：**資料表若要保存圖片、影片等二進位資料，欄位應該使用什麼型別，以及容量要選多大。**

文字欄位是為文字內容設計的；圖檔則是由 `0`、`1` 所代表的二進位內容組成。MySQL 提供 `BLOB` 類型來保存這類資料。不過，只知道要用 `BLOB` 還不夠，因為課堂介紹的三種容量差距很大：

- `BLOB`：約 65 KB
- `MEDIUMBLOB`：約 16 MB
- `LONGBLOB`：約 4.2 GB

如果欄位容量選得太小，實際檔案便可能放不進去。例如，課堂指出一般拍攝的 JPG、PNG 圖片可能落在 3～10 MB，因此約 65 KB 的 `BLOB` 通常只適合較小的圖示；要保存一般圖片，課堂建議至少考慮 `MEDIUMBLOB`。

本課最後在 MySQL Workbench 示範建立名為 `image`、型別為 `MEDIUMBLOB` 的欄位。逐字稿沒有示範如何把檔案實際寫入或讀出。

## 2. 核心概念

### 概念一：二進位資料

- **它是什麼**：由位元內容構成的資料。課堂以圖片為主要例子，並用「0101」幫助理解。
- **為什麼存在**：電腦中的圖片等檔案不是一般文字，資料庫必須用能容納原始二進位內容的欄位保存它們。
- **解決什麼問題**：讓圖片、影片等非文字內容可以成為資料表欄位的值。
- **何時使用**：資料表確實需要直接保存圖檔或影片內容時。
- **何時不適合使用**：欄位只需保存一般文字時。本課未比較「把檔案放在資料庫」與「只在資料庫保存檔案路徑」兩種設計，因此不能根據本課判定哪一種較好。

### 概念二：`BLOB` 是二進位大型物件

- **它是什麼**：`BLOB` 是 Binary Large Object 的縮寫，是 MySQL 用來保存二進位資料的類型。
- **為什麼存在**：二進位檔案需要不同於文字的儲存方式。
- **解決什麼問題**：讓資料表欄位可以保存圖片等二進位內容。
- **何時使用**：欄位值是二進位檔案內容時。
- **何時不適合使用**：要保存的是一般文字，或檔案大小超過所選 `BLOB` 類型的容量時。

### 概念三：容量分級必須配合檔案大小

- **它是什麼**：課堂介紹 `BLOB`、`MEDIUMBLOB`、`LONGBLOB` 三種容量級別。
- **為什麼存在**：圖示、照片與影片的檔案大小可能相差非常大，單一容量級別不一定適合所有情境。
- **解決什麼問題**：讓欄位容量能符合預計保存的檔案。
- **何時使用**：設計資料表時，先估計實際檔案大小，再選擇足以容納它的級別。
- **何時不適合使用**：不能只看到「圖片」就固定選某一型別；課堂也指出圖片大小會受拍攝解析度影響。

### 概念四：欄位型別決定可接受的資料規模

- **它是什麼**：建立資料表欄位時，為欄位指定的型別會限制它能容納的資料大小。
- **為什麼存在**：資料庫需要明確知道欄位預定保存哪一類資料及其規模。
- **解決什麼問題**：在真正存入檔案之前，先為資料配置合適的欄位。
- **何時使用**：建立或設計資料表時。本課的具體做法是在 Workbench 對 `Tables` 按右鍵、選擇 `Create Table`，再建立 `image` 欄位並選 `MEDIUMBLOB`。
- **何時不適合使用**：逐字稿沒有說明現有欄位如何修改，也沒有說明實際匯入圖片的操作，因此不能把建好欄位誤認為已經存入圖片。

### 延伸知識：`NULL` 表示欄位可以沒有值

以下 SQL 是把課堂中的 Workbench 操作寫成指令：

```sql
CREATE TABLE `blob`
(
    image MEDIUMBLOB NULL
);
```

整段指令的目的是：**建立一張名為 `blob` 的資料表，裡面有一個可保存二進位資料、也允許暫時沒有值的 `image` 欄位。**

依照執行時的閱讀順序拆開來看：

1. `CREATE TABLE`：要求 MySQL 建立一張新資料表。
2. `` `blob` ``：新資料表的名稱是 `blob`。名稱外的反引號 `` ` ` `` 告訴 MySQL 這裡是識別名稱，避免把 `blob` 當成型別名稱來解析。實務上使用 `images` 等更能表達用途的名稱會比較清楚。
3. `(` 與 `)`：括號內列出這張表有哪些欄位；此處只有一個欄位。
4. `image`：欄位名稱。每一筆資料都會有一個名為 `image` 的位置。
5. `MEDIUMBLOB`：欄位型別。依課堂說明，它可保存約 16 MB 的二進位資料。
6. `NULL`：允許這個欄位沒有值。例如先建立一筆資料、之後才補圖片時，`image` 可以暫時是 `NULL`。
7. `;`：表示這一條 SQL 指令結束。

`NULL` 必須與另外兩種情況分開：

| 欄位內容 | 意思 |
| --- | --- |
| `NULL` | 沒有提供圖片值，或圖片值未知 |
| 空的二進位資料 | 有一個值，但內容長度是 0 |
| 實際圖片的二進位資料 | 有值，而且內容是圖片資料 |

具體來說：

- 若新增一筆資料時沒有提供圖片，而且欄位允許 `NULL`，`image` 可以保持 `NULL`。
- 若欄位改成 `image MEDIUMBLOB NOT NULL`，便表示每一筆資料都不允許在這個欄位使用 `NULL`。
- `NULL` 不是字串 `"NULL"`，也不代表已經放入一個空白圖片。

在 MySQL 中，欄位沒有明寫 `NULL` 或 `NOT NULL` 時，通常預設允許 `NULL`；這裡把 `NULL` 寫出來，是明確表達設計意圖。逐字稿沒有解釋這段 SQL 與 `NULL`，所以本段屬於延伸知識。

## 3. Mental Model

可以把選擇欄位型別理解成「先量物品，再選容器」：

```text
要保存的檔案
    ↓
判斷它是不是二進位資料
    ↓ 是
估計實際檔案大小
    ↓
選擇容得下它的 BLOB 級別
    ↓
在資料表建立欄位
    ↓
之後才可能把檔案內容存入欄位
```

以課堂範例來走一次：

1. 要保存的值是 JPG 或 PNG 圖片，不是一般文字。
2. 圖片可能有 3～10 MB，大小也會受到拍攝解析度影響。
3. 約 65 KB 的 `BLOB` 容量不足以涵蓋這個範圍。
4. 約 16 MB 的 `MEDIUMBLOB` 能容納課堂所舉的一般圖片範圍。
5. 因此在 Workbench 建立 `image` 欄位，並把型別設為 `MEDIUMBLOB`。

白話來說，`image` 是欄位名稱，表示這一格預計放圖片內容；`MEDIUMBLOB` 是欄位型別，表示這一格允許保存的資料種類與容量級別。建立欄位只是準備好容器，並不等於已經把圖片放進去。

## 4. 專家視角

### 初學者需要知道，但資深工程師通常不會特別思考的內容

- **圖片不是文字**：圖片在資料庫中要當成二進位內容處理，不能因為副檔名是 `.jpg` 或 `.png`，就把它理解成一段普通字串。
- **欄位名稱與欄位型別是兩件事**：`image` 只是在描述欄位用途；真正讓欄位能保存二進位內容的是 `MEDIUMBLOB` 型別。
- **建欄位不等於存資料**：課堂只完成欄位建立。實際寫入及讀取二進位檔案的流程，逐字稿未涵蓋。

### 即使是資深工程師仍然會注意的內容

- **用真實資料大小決定型別**：圖片大小會受到解析度等因素影響。不能只用「這是圖片」作判斷，還要檢查實際大小分布與最大值。
- **容量不足會直接影響資料能否保存**：若預計存入 3～10 MB 的照片，卻選擇課堂所說約 65 KB 的 `BLOB`，資料模型一開始就不符合需求。
- **不要無根據地選最大型別**：課堂呈現了不同容量級別，但沒有分析一律使用 `LONGBLOB` 的成本。因此能確定的原則只有：型別必須足夠容納需求；更細的效能與儲存取捨屬於逐字稿未涵蓋的內容。

## 5. 語法 vs 通用知識

### 語言特有知識

- MySQL 使用 `BLOB` 表示 Binary Large Object。
- 本課介紹 `BLOB`、`MEDIUMBLOB`、`LONGBLOB` 三種容量級別。
- MySQL Workbench 可透過 `Tables` → 右鍵 → `Create Table` 建立欄位，再把 `image` 欄位設為 `MEDIUMBLOB`。
- 在欄位定義 `image MEDIUMBLOB NULL` 中，`image` 是欄位名稱、`MEDIUMBLOB` 是資料型別，而 `NULL` 表示該欄位允許沒有值；相反的限制寫作 `NOT NULL`。

這些名稱與操作方式屬於 MySQL 及 MySQL Workbench 的具體機制，換成其他資料庫時，型別名稱和操作介面可能不同。

### 通用程式設計知識

- **資料型態要符合資料本質**：文字與二進位檔案是不同種類的資料，應用不同方式處理。
- **容量規劃要根據真實輸入**：先了解資料可能有多大，再決定儲存容器。
- **資料模型會限制後續行為**：欄位設計不是只有命名；型別選擇會決定後續資料能否存入。

這些原則不只適用於 MySQL。換成其他資料庫、程式語言的位元組陣列，甚至上傳檔案大小限制時，都仍需先判斷資料類型與容量上限。

## 6. Trade-off

### `BLOB` vs `MEDIUMBLOB` vs `LONGBLOB`

| 選擇 | 課堂所述容量 | 適合情境 | 選得太小的後果 | 課堂未說明的部分 |
| --- | ---: | --- | --- | --- |
| `BLOB` | 約 65 KB | 小型圖示，例如課堂舉的 200×200 像素圖示 | 一般照片可能放不下 | 精確檔案大小不能只由像素尺寸判定 |
| `MEDIUMBLOB` | 約 16 MB | 課堂所舉約 3～10 MB 的 JPG、PNG 照片 | 超過容量的檔案仍放不下 | 實際寫入方法與效能成本 |
| `LONGBLOB` | 約 4.2 GB | 課堂舉例的影片等大型內容 | 若檔案超過上限仍不適用 | 儲存大型影片的效能、備份與傳輸影響 |

這項選擇的核心不是「越大越好」，而是讓容量符合資料需求。逐字稿清楚說明了容量差異及適合的檔案規模，但沒有提供不同型別在效能、磁碟使用量或維護成本上的比較，因此這些部分不能由本課直接下結論。

## 7. 常見誤解

1. **看到圖片就選 `BLOB`，不必看大小。** `BLOB` 是一類二進位型別，但課堂介紹的各級容量不同；一般照片可能遠超過約 65 KB。
2. **圖片解析度相同，檔案大小就一定相同。** 課堂只說解析度會影響檔案大小，沒有說解析度是唯一因素；因此仍應以實際檔案大小為準。
3. **把欄位命名為 `image`，它就能保存圖片。** 欄位名稱沒有決定資料能力；必須把型別設成合適的 `BLOB` 類型。
4. **建立 `MEDIUMBLOB` 欄位後，圖片已經進入資料庫。** 建立欄位只是準備儲存空間，實際存入資料是另一個步驟，而本課沒有示範。
5. **`LONGBLOB` 容量最大，所以所有二進位欄位都應選它。** 本課只支持「容量要足夠」；沒有支持所有情況都選最大型別。
